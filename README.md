# compxctl

**Частота опроса и DPI для мышей CompX / Ardor Gaming в Linux — без фирменной утилиты для Windows.**

CLI из одного Python-файла. Делает две вещи, которые живут в совершенно разных местах, и намеренно их не смешивает:

| Что | Где живёт | Как это делает compxctl | Нужны пакеты |
|---|---|---|---|
| Частота опроса | в цикле опроса USB на стороне хоста | `usbhid.mousepoll` + дескриптор эндпоинта в sysfs | **никаких** |
| DPI, батарея, конфиг-память | внутри чипа мыши | проприетарный HID-протокол через `/dev/hidraw*` | **никаких** |

Зависимостей нет вообще: и sysfs, и hidraw доступны стандартной библиотеке Python. Это отдельно проверяется тестом, который читает AST самого `compxctl.py`.

```console
$ compxctl rate
Device: 2.4G Dual Mode Mouse (25a7:fa7b)
Device advertises: 1000 Hz (1ms via interval, ep_81)
Host override: none (usbhid.mousepoll = 0)
Effective: 1000 Hz (from device descriptor)
```

English: [README.en.md](README.en.md)

## Зачем это и почему переписано

Первая версия меняла частоту опроса записью в EEPROM мыши через реверс-инжиниренный протокол. Это работает — проверено на железе, — но это самый хрупкий и наименее переносимый способ: необратимо, ограничено ресурсом записи, неприменимо к другой мыши и завязано на одну пойманную прошивку.

Linux и так отдаёт частоту опроса нормально. Хост опрашивает interrupt-эндпоинт с интервалом, который объявляет устройство, а `usbhid` умеет этот интервал переопределить для всех мышей сразу. Поэтому:

* **Чтение частоты** — это чтение sysfs: точно, мгновенно, без движения мыши, без подсчёта событий, без зависимостей. Прежний `check` полторы секунды считал события ввода и показывал примерно вдвое больше реального, стоило двинуть мышь по диагонали: один отчёт мыши несёт и `REL_X`, и `REL_Y`, а счётчик считал оба. Команда удалена, её место занял `rate`.
* **Установка частоты на хосте** — одна запись в `/sys/module/usbhid/parameters/mousepoll`. Обратимо, без EEPROM, без вендорского протокола.
* **Запись интервала в устройство** осталась, потому что это единственный способ изменить настройку самой мыши, но теперь это явный opt-in за `--persist`.

В 3.0 устройство больше не открывается через libusb: конфиг-интерфейс — это HID-интерфейс, им владеет `usbhid`, и ядро само отдаёт его в user space как узел `/dev/hidrawN`. Отсюда два следствия: `pyusb` больше не нужен, а `status` и `battery` перестали дёргать мышь — раньше libusb отключал драйвер ядра на время команды, и курсор на мгновение замирал.

## Как это устроено

Разбор дескриптора отчётов конфиг-интерфейса (189 байт, снято с проверенного экземпляра) объясняет весь протокол:

| Отчёт | Тип | Длина | Что это |
|---|---|---|---|
| id 6 | FEATURE | 7 байт | первый «живой» пакет интервала |
| id 8 | FEATURE | 16 байт | чтение/запись конфиг-памяти, запрос батареи |
| id 9 | INPUT | 16 байт | все ответы прошивки |

Поэтому запрос уходит одним `fcntl.ioctl` с `HIDIOCSFEATURE` (это и есть `SET_REPORT` нужного типа), а ответ читается из очереди входных отчётов. `HIDIOCGFEATURE` (`GET_REPORT`) на этой прошивке возвращает 17 нулевых байт — ответ приходит только входным отчётом, и это не догадка, а измерение.

Кроме ответов интерфейс шлёт свой трафик: подтверждение на каждый «живой» пакет (`09 11 …`) и на каждую запись в конфиг-память (`09 07 …`, эхо записанных байт). Всё это фильтруется по коду операции, адресу и контрольной сумме, а не принимается за ответ.

## Установка

```console
$ pip install .        # ставит команду compxctl, ставить больше нечего
```

Или просто скопируйте `compxctl.py` — он работает на голом Python 3.10+ без установки. Для работы с устройством нужен доступ к `/dev/hidraw*` (см. «Права доступа»); для чтения sysfs не нужно ничего.

## Использование

### Частота опроса

```console
$ compxctl rate                 # показать: устройство, переопределение хоста, итог
$ sudo compxctl rate host 1000  # на стороне хоста, для всех USB-мышей, обратимо
$ compxctl rate device 1000 --persist      # плюс запись в EEPROM мыши
```

`rate host` пишет `usbhid.mousepoll`, а это действует на **все USB-мыши** в системе. Настройка не переживает перезагрузку, и способ сделать её постоянной зависит от того, как собран `usbhid` — команда сама печатает нужную строку:

* **загружаемый модуль** — `options usbhid mousepoll=1` в `/etc/modprobe.d/`
* **встроен в ядро** — `usbhid.mousepoll=1` в командной строке ядра, потому что `/etc/modprobe.d/` для встроенных модулей молча игнорируется

Инструмент определяет случай сам (`usbhid_is_builtin()` читает `/lib/modules/$(uname -r)/modules.builtin`). Это не гипотетика: на машине, где это писалось, `usbhid` встроен, и лежавший в `/etc/modprobe.d/mousepoll.conf` файл не делал ровно ничего.

`rate device HZ --persist` шлёт два «живых» пакета интервала и кадр записи в EEPROM, читает значение назад и **сам перезагружает порт**, чтобы не просить вас лезть под стол за ресивером:

```console
$ compxctl rate device 500 --persist
Device EEPROM updated to 500 Hz (0x02).
  Port reset: the receiver re-enumerated, and the host re-read the descriptors; the endpoint advertises 1000 Hz (1ms, ep_81).
  That is expected: on this unit the stored interval does not change the endpoint, which stays at 1ms — the stored value is what the device itself sends at.
```

Без `--persist` команда отказывается работать, а если в устройстве уже лежит нужное значение — не пишет ничего и порт не трогает. Флаг `--no-reset` оставляет перезагрузку порта человеку: команда запишет значение и напомнит переткнуть мышь (полезно, если ресивер общий с клавиатурой и её исчезновение вам мешает).

Перезагрузка порта — это `USBDEVFS_RESET` на `/dev/bus/usb/BBB/DDD`; ядро пишет об этом в журнал (`usb 3-2: reset full-speed USB device number 2`), так что её легко проверить. Если прав на узел нет, команда не падает: она сообщает, что порт не сброшен, и предлагает переткнуть мышь.

Что выбрать:

* **«Хочу 1000 Гц в Linux прямо сейчас»** → `rate host 1000`. В мышь не пишется ничего.
* **«Настройка должна ехать вместе с мышью»** → `rate device 1000 --persist`.
* **«Хочу 125/500 Гц»** → лучше путь через устройство: если заставить хост опрашивать раз в 8 мс, это замедлит **все** мыши, включая 1000-герцовую.

### DPI

```console
$ compxctl dpi list
  slot  addr    x    y    mul  crc   value
  *0   0x000C  07   07   00   47    400
   1   0x0010  13   13   00   2F    1000
   2   0x0014  1F   1F   00   17    1600
   3   0x0018  2F   2F   00   F7    2400
   4   0x001C  77   77   00   67    6000
   5   0x0020  7F   7F   00   57    6400
   6   0x0024  EF   EF   00   77    raw:0xEF
   7   0x0028  7B   7B   44   1B    raw:0x7B(mul=0x44)
Active DPI level: slot 0 (index 0x01)

$ compxctl dpi 2400              # записать в слот активного уровня
$ compxctl dpi --slot 3 2400     # записать в явный слот 0..5
```

Хранится не само значение, а код: `DPI / 50 - 1`, поэтому DPI должен быть кратен 50 в диапазоне 50..6400. Каждая запись проверяется чтением **всех четырёх байт** назад.

Слоты 6 и 7 на проверенном экземпляре держат нерасшифрованную расширенную кодировку: они показываются сырыми байтами и никогда не перезаписываются. Если регистр активного уровня (`0x0004`) не содержит корректного индекса 1..8, `dpi N` отказывается угадывать и просит `--slot` — прежняя версия в этом случае молча писала в слот 0.

### Остальное

```console
$ compxctl status
Device: 2.4G Dual Mode Mouse (25a7:fa7b)
Device advertises: 1000 Hz (1ms via interval, ep_81)
Host override: none (usbhid.mousepoll = 0)
Effective: 1000 Hz (from device descriptor)
Stored rate: 1000 Hz (config memory 0x0000)
Active DPI level: index 0x01 (0x0004) -> slot [0]: 400
DPI slots: [0] 400 <- active [1] 1000 [2] 1600 [3] 2400 [4] 6000 [5] 6400 [6] raw:0xEF [7] raw:0x7B(mul=0x44)
Battery: 95% (charging) [2.4G mode]

$ compxctl battery
Battery: 95% (charging) [2.4G mode]

$ compxctl probe --start 0x0000 --length 0x20
0x0000: 01 54 05 50 01 54 00 55
0x0008: 00 55 01 54 07 07 00 47
0x0010: 13 13 00 2f 1f 1f 00 17
0x0018: 2f 2f 00 f7 77 77 00 67
Interpretation:
  0x0000 stores the interval code 0x01 = 1000 Hz
  slot 0: 07 07 00 47 (checksum OK)
  ...
```

`status` сопоставляет то, что объявляет устройство (`1ms`), с тем, что лежит в его EEPROM (`0x0000`), — если они разойдутся, это будет видно.

### Машиночитаемый вывод: `--json`

`rate`, `status`, `dpi` и `battery` умеют `--json` — ровно один JSON-документ в stdout, пригодный для Waybar, Polybar, i3status или скрипта:

```console
$ compxctl battery --json | jq -r '.battery.percent'
95
$ compxctl status --json | jq '{rate: .polling.effective_rate_hz, dpi: .active_dpi.dpi}'
{
  "rate": 1000,
  "dpi": 400
}
$ compxctl status --json | jq '.dpi_slots[] | select(.active) | .text'
"400"
```

Правила, на которые можно опираться:

* ошибка выполнения — это **один** JSON-документ в stdout: `{"schema": 1, "command": "status", "error": {"message": "..."}}`, код возврата при этом `1`;
* ошибка в аргументах командной строки (код `2`) остаётся текстом в stderr и документа не даёт: это опечатка в скрипте, а не состояние устройства;
* неизвестное значение — это `null`, а не строка `"n/a"`;
* `status` читает четыре вещи сразу и не падает из-за одной: то, что не прочиталось, уходит в массив `warnings`, остальное остаётся на месте. `dpi` и `battery` читают по одной вещи и в таком случае отдают документ с `error`;
* ключ `schema` меняется только тогда, когда меняется смысл ключей; добавление новых его не трогает.

`status --json` не дёргает драйвер и не мешает мыши, поэтому его можно звать из статус-бара хоть каждую секунду — пока устройство отвечает, это единицы миллисекунд. Неотвечающее устройство упирается в таймаут на каждое чтение, и тогда `status` может идти до ~14 секунд (4 чтения × 4 попытки × 500 мс); для бара это повод держать свой таймаут.

## Права доступа

* `rate` на чтение не требует ничего.
* `rate host` требует root — это запись в параметр модуля ядра.
* Командам устройства нужен доступ к узлу `/dev/hidraw*`, а для `--persist` ещё и к узлу USB (перезагрузка порта). Проще всего поставить udev-правило из репозитория:

```console
$ sudo cp 99-compx-mouse.rules /etc/udev/rules.d/
$ sudo udevadm control --reload-rules && sudo udevadm trigger
```

```udev
SUBSYSTEM=="hidraw", ATTRS{idVendor}=="25a7", TAG+="uaccess"
SUBSYSTEM=="usb", ENV{DEVTYPE}=="usb_device", ATTRS{idVendor}=="25a7", TAG+="uaccess"
```

`TAG+="uaccess"` покрывает активную сессию logind. Правило на `usb_device` нужно только для перезагрузки порта: без него `rate device --persist` запишет значение, но порт не сбросит и скажет об этом. Разово можно просто `sudo`.

`./install.sh` не затирает существующее правило молча: если файл на месте и отличается, старая версия сохраняется рядом как `99-compx-mouse.rules.bak.<дата>`, а `--uninstall` говорит, где лежат такие копии.

Учтите: `GROUP="users"` как запасной вариант — ловушка. Доступ к устройствам идёт не через эту группу, и состоит ли в ней пользователь, решает установщик: там, где не состоит никто, правило молча ничего не даёт. Проверить у себя — `id -nG`. Если у вас стоят правила 2.x — переустановите их: строки для узла `hidraw` в них не было.

## Поддерживаемые устройства

USB vendor `0x25A7`, product id `0xFA7B`, `0xFA7C`, `0xFA03`, `0xFA93`. Протокол перехвачен и проверен на Ardor Gaming Ulta (PID `0xFA7B`); соседние id обслуживаются тем же кодом, но по отдельности не проверялись.

## Коды возврата

| Код | Значение |
|---|---|
| `0` | успех |
| `1` | ошибка выполнения — нет устройства, нет прав, плохой ответ, отказ проверки чтением назад |
| `2` | ошибка аргументов командной строки (argparse) |
| `130` | прервано по Ctrl+C |

С `--json` ошибка выполнения приходит документом в stdout, код возврата не меняется.

## Тесты

```console
$ pip install pytest && pytest
```

185 тестов, которым не нужны ни железо, ни root, ни `/dev/hidraw`, ни сторонние пакеты: слой устройства работает через поддельный hidraw-ввод-вывод, слой sysfs — через синтетическое дерево, включая поиск узла `hidraw` по дереву sysfs. Отдельно зафиксированы настоящие ошибки, найденные на живом железе:

* поиск узла `hidraw` мог вернуть узел интерфейса движения вместо конфиг-интерфейса — `SET_REPORT` туда возвращает `EPIPE`;
* проверка чтением назад принимала подтверждение записи за ответ, а повторная отправка команды оставляла в очереди лишний ответ — из-за этого успешная запись в EEPROM выглядела как ошибка;
* разбор hex-атрибутов USB-дескриптора и частичная проверка readback у DPI (принимала неверный `y`) — из ревью прошлой версии.

Отдельный тест читает AST `compxctl.py` и падает, если в нём появится импорт не из стандартной библиотеки.

## Что проверено на железе

Всё ниже измерено на Ardor Gaming Ulta (`25a7:fa7b`), ядро 7.2.9, не по документации:

* **hidraw вместо libusb.** Чтение конфиг-памяти, DPI, батареи и запись кадров дают побайтово те же ответы, что прежний путь через libusb, но без отключения драйвера ядра.
* **Перезагрузка порта работает и без root** (при установленном udev-правиле): `USBDEVFS_RESET` возвращает `0`, ядро пишет `usb 3-2: reset full-speed USB device number 2 using xhci_hcd`.
* **Проверка чтением назад действительно ловит сбой.** На одном из прогонов запись 500 Гц отчиталась как неуспешная — и это было верно: испортилась не запись, а чтение (в очереди лежал ответ на предыдущую команду). После починки фильтра запись и чтение сходятся, а `probe` подтверждает значения `0x01`/`0x02` в `0x0000`.
* **Дескриптор не следует за EEPROM.** С записанным кодом `0x02` (500 Гц) интерфейс по-прежнему объявляет `bInterval = 01`, то есть 1 мс; с `0x01` — тоже. Проверено с обеих сторон перезагрузки порта. Значит, прежняя формулировка «переткните мышь, чтобы хост перечитал дескриптор» объясняла эффект неправильно: в дескрипторе ничего не меняется, а хранимый код задаёт то, с какой частотой отправляет сама мышь. Это уже вывод, а не измерение: чтобы увидеть его напрямую, нужно считать входные отчёты при движении мыши.
* **Полный дамп конфиг-памяти до и после всех экспериментов совпадает** — запись не задела ни счётчик уровней DPI (`0x0002`), ни активный индекс (`0x0004`), ни слоты.

## Ограничения

* Путь через EEPROM по-прежнему реверс-инжинирен и по-прежнему ограничен ресурсом записи. `--persist` — единственная команда, которая туда пишет, и она проверяет результат чтением назад и сверяет кадр с проверенным на железе захватом.
* `rate host` не умеет «только эту мышь» — `mousepoll` глобальный.
* Слоты 6-7 используют нерасшифрованную кодировку и не перезаписываются.
* Перезагрузка порта сбрасывает **всё устройство** приёмника. Если на том же ресивере висит ещё и клавиатура, она на секунду пропадёт — для этого есть `--no-reset`.
* Частоту, с которой мышь реально отправляет отчёты, инструмент не измеряет: для этого нужно движение мыши, а считать события ввода, как делал удалённый `check`, — способ получить неверное число.
